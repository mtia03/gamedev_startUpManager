# 재무 시스템 설계 — 자산 / 부채 / 자본

> **문서 범위**: 기획만. 구현은 포함하지 않는다.
> 시작 자금을 자본금으로 보고, 사업 수행을 회계 흐름으로 옮긴다.
> 판매 활동은 만들지 않는다 — **사업 수주 → 수익, 인건비·설비 → 비용**이 전부다.

관련: [`project-scale-spec.md`](project-scale-spec.md) · [`llm-prompt-design.md`](llm-prompt-design.md)

## 0. 현재 돈이 오가는 지점

지금 구현된 현금 증감은 6곳뿐이다. 회계 모델은 이걸 분개로 바꾸는 작업이다.

| 위치 | 사건 | 현재 처리 |
|------|------|----------|
| `start()` | 창업 | 난이도별 시작 자금 |
| `advance_week()` | 주급 지급 | `funds -= payroll` |
| `progress_businesses()` | 사업 완료 | `funds += payout` |
| `upgrade_office()` | 사무실 확장 | `funds -= cost` |
| `abandon_business()` | 사업 포기 | `funds -= penalty` |
| `fire_developer()` | 해고 | `funds -= severance` |

## 1. 가장 큰 판단 — 엄밀하게 vs 직관적으로

### 결론: **중간. "발생주의 라이트"를 권한다.**

| 방식 | 장점 | 단점 |
|------|------|------|
| 현금주의 (지금) | 이해가 쉽다 | 사업 완료 전까지 계속 적자, 완료 시 왕창 흑자. **판단할 게 없다** |
| 완전 발생주의 | 정확하다 | 이연·충당금까지 가면 게임이 아니라 회계 과제가 된다 |
| **발생주의 라이트** | 이익과 현금이 갈린다 | 개념 하나를 가르쳐야 한다 |

### 왜 중간인가 — **흑자도산이 만들어진다**

수주산업은 **진행기준(percentage of completion)** 으로 수익을 인식한다.
이 게임에는 이미 **업무 진행률**이 있으므로 그대로 쓸 수 있다.

```
누적 인식수익 = 계약금액 × 전체 진행률
이번 주 수익  = 누적 인식수익 − 지난주까지 인식수익
```

이러면 이런 상황이 생긴다.

> 사업은 순조롭고 **손익계산서는 흑자**인데,
> 대금은 완료 시점에 들어오므로 **현금이 말라 급여를 못 준다.**

이게 경영 게임에서 가장 배울 만한 지점이고, 지금 파산 규칙(급여 미지급 → 즉시 파산)과
정확히 맞물린다. **"이익 ≠ 현금"** 하나만 가르치면 나머지는 직관으로 읽힌다.

### 대신 버리는 것

- 감가상각은 **정액법만**, 잔존가치 0
- 이연법인세·충당부채·재고자산 **없음**
- 현금흐름표 **만들지 않는다** (현금 잔액과 주간 증감만 보여줌)

## 2. 계정 구조

항목을 **10개 안쪽**으로 묶는다. 더 늘리면 화면에서 못 읽는다.

### 자산

| 계정 | 뜻 | 증가 | 감소 |
|------|-----|------|------|
| **현금** | 지금 쓸 수 있는 돈 | 착수금·잔금 수령, 차입 | 급여, 설비 구매, 이자, 상환 |
| **미청구공사** | 일은 했는데 아직 못 받은 돈 | 진행률만큼 수익 인식 | 대금 수령 시 상계 |
| **설비** | 사무실·장비의 장부가 | 구매 | 매주 감가상각 |

> **미청구공사**가 이 게임의 핵심 계정이다. "장부상 자산은 늘어나는데
> 통장은 비어간다"를 눈으로 보여준다.

### 부채

| 계정 | 뜻 | 발생 |
|------|-----|------|
| **미지급급여** | 못 준 급여 | 자금 부족으로 급여 미지급 시 |
| **선수금** | 일하기 전에 받은 돈 | 사업 착수금 수령 |
| **차입금** | 빌린 돈 | 대출 실행 |

### 자본

| 계정 | 뜻 |
|------|-----|
| **자본금** | 창업 시 시작 자금. **끝까지 고정** |
| **이익잉여금** | 누적 순이익. 적자가 쌓이면 음수(결손금) |

```
자산 = 부채 + 자본
현금 + 미청구공사 + 설비 = 미지급급여 + 선수금 + 차입금 + 자본금 + 이익잉여금
```

## 3. 수익 · 비용

### 수익

| 항목 | 인식 시점 |
|------|----------|
| **사업 수익** | 매주, 진행률 증가분만큼 |

### 비용

| 항목 | 인식 시점 | 지금 있는 것 |
|------|----------|-------------|
| **노무비** | 매주 발생 | `weekly_payroll()` |
| **감가상각비** | 매주 발생 | 신규 |
| **이자비용** | 매주 발생 | 신규 |
| **위약금** | 사업 포기 시 일시 | `ABANDON_PENALTY_RATE` |
| **퇴직금** | 해고 시 일시 | 4주치 급여 |

> **노무비를 배치 여부로 나눌지**는 열어둔다.
> 업무에 투입된 인원의 급여를 매출원가, 대기 인원을 판관비로 가르면
> "놀리는 인력의 비용"이 숫자로 드러난다. 다만 계정이 하나 늘어난다.

## 4. 유형자산 — 설비

### 4-0. 설계 원칙

설비를 **등급에만** 묶으면 "T3 하려면 8만 달러"라는 계단일 뿐이고,
어떤 사업을 하든 똑같아서 선택이 없다.

**필드(직무) 축을 주축으로 삼는다.** 그러면 이렇게 맞물린다.

```
어떤 분야 인력을 뽑았나  →  어떤 설비를 살까  →  어떤 사업을 수주할까
```

AI 전문가를 모았으면 GPU를 사고 AI 사업을 받는다. 모바일 팀이면 실기기 랩을 산다.
**전문화가 자산 구성으로 드러난다.**

### 4-1a. 전제 — 사업에 "종류"가 필요하다

**현재 구조의 문제**: 사업 이름은 `BUSINESS_NAMES`에서, 필드는 `FIELDS`에서
**각각 따로** 랜덤으로 뽑는다 (`business_model.py:202, 226`).
그래서 `"추천 엔진"`인데 AI 업무가 없고 `"헬스케어 앱"`인데 모바일이 없는 일이 생긴다.

이름과 내용이 따로 놀면 **"이 종류엔 이 설비"가 성립할 수 없다.**
종류를 정의해야 아래가 한 줄로 꿰인다.

```
사업 종류  →  필드 조합  →  필요 설비  →  자산 구성
```

#### 사업 종류 (genre)

같은 등급이라도 종류가 다르면 **필요한 인력도 설비도 달라진다.**

| 종류 | 핵심 필드 (반드시) | 부가 필드 (확률) | 성격 |
|------|------------------|-----------------|------|
| **사내 도구** | FE, BE | UIUX | 저난도. 초반 진입로 |
| **커머스** | FE, BE | UIUX, Ops | 무난. 가장 흔함 |
| **모바일 앱** | Mobile, UIUX | BE | 실기기 랩 필요 |
| **AI · 데이터** | AI, BE | Ops | 설비가 비싸고 보상이 높다 |
| **인프라 · 플랫폼** | Ops, BE | FE | 설비가 무겁고 기간이 길다 |
| **실시간 · 게임** | Mobile, BE, Ops | FE, UIUX | 필드가 넓어 인력 요구가 크다 |

- 업무 개수는 지금처럼 **등급**이 정한다. 핵심 필드를 먼저 채우고
  남는 자리를 부가 필드에서 뽑는다
- 등급이 낮아 자리가 모자라면 핵심 필드 중 일부만 들어간다
- 이름도 종류 안에서 뽑는다 → `"추천 엔진"`은 항상 AI·데이터 종류

#### 종류별 보상·기간 보정

같은 등급 안에서도 차등을 준다. **위험한 종류가 더 준다.**

| 종류 | 보상 배율 | 목표 기간 | 이유 |
|------|:--------:|:--------:|------|
| 사내 도구 | ×0.85 | ×0.9 | 쉽고 짧다 |
| 커머스 | ×1.00 | ×1.0 | 기준 |
| 모바일 앱 | ×1.10 | ×1.0 | 설비 부담 |
| AI · 데이터 | ×1.35 | ×1.1 | 설비가 가장 비싸다 |
| 인프라 · 플랫폼 | ×1.20 | ×1.2 | 길게 묶인다 |
| 실시간 · 게임 | ×1.25 | ×1.1 | 인력 폭이 넓어야 한다 |

> 이러면 **"우리는 커머스 전문 회사"** 같은 정체성이 생긴다.
> 커머스 설비(FE·BE·UIUX)만 갖추고 그 종류만 골라 받는 전략이 성립하고,
> AI 사업에 손대려면 GPU 투자를 결심해야 한다.

#### 명성과 종류 해금

지금 등급은 명성으로 열린다(`REPUTATION_UNLOCK`). 종류도 같은 방식을 쓸 수 있다.

| 종류 | 해금 명성 |
|------|---------:|
| 사내 도구 · 커머스 | 0 |
| 모바일 앱 | 3,000 |
| 인프라 · 플랫폼 | 6,000 |
| AI · 데이터 | 8,000 |
| 실시간 · 게임 | 10,000 |

→ 초반엔 저비용 종류만 들어와서 설비 부담이 자연스럽게 낮다.

### 4-1. 분야별 전문 설비 (주축)

업무의 **필드**를 보고 필요 설비가 정해진다.

| 필드 | 설비 | 취득가 | 내용연수 | 미보유 페널티 |
|------|------|-------:|:--------:|:------------:|
| UIUX | 디자인 툴 · 사용성 테스트실 | $25,000 | 52주 | 처리량 −10% |
| FE | 크로스브라우징 테스트 환경 | $30,000 | 52주 | −15% |
| BE | DB · 부하 테스트 서버 | $55,000 | 78주 | −15% |
| Mobile | 실기기 테스트 랩 | $70,000 | 52주 | −20% |
| Ops | 스테이징 · 모니터링 인프라 | $110,000 | 78주 | −25% |
| AI | GPU 학습 서버 | $180,000 | 78주 | **−35%** |

- **AI가 가장 비싸고 페널티도 크다.** "AI 사업은 진입장벽이 높다"가 자연스럽게 생긴다
- UIUX는 싸고 페널티도 작다 — 초반에 접근하기 쉬운 분야
- 모바일 랩은 단말이 빨리 낡아 내용연수가 짧다

### 4-2. 등급이 페널티 강도를 정한다

같은 설비 미보유라도 규모에 따라 타격이 다르다. **초반은 설비 없이도 굴러가야 한다.**

| 등급 | 페널티 배율 | 실질 (AI 기준) |
|:----:|:----------:|:-------------:|
| T1 | ×0 | 없음 |
| T2 | ×0.4 | −14% |
| T3 | ×0.7 | −24.5% |
| T4 | ×1.0 | −35% |
| T5 | ×1.3 | **−45.5%** |

T1은 설비 없이 그냥 한다. T5는 설비 없이 사실상 불가능하다.

### 4-3. 공통 인프라 (규모 축)

분야와 무관하게 회사 전체가 쓰는 것. **사무실 레벨과 연동**한다.

| 항목 | 취득 | 비고 |
|------|------|------|
| 사무 집기 | 사무실 확장 비용에 포함 | 이미 구현됨 (레벨 1~3) |
| 개발 서버 | $40,000 / 대 | **1대당 동시 사업 2건** 감당 |

개발 서버는 **수용량** 개념이다. 사업을 3건 동시에 굴리려면 2대가 필요하다.
초과하면 모든 업무 처리량 −10%. 책상과 같은 논리라 이해가 쉽다.

### 4-4. 수용량 — 등급이 오르면 여러 대

분야별 설비도 **1대가 업무 2개**를 감당한다.

| 등급 | 업무 수 | 필요 대수 (해당 분야) |
|:----:|:------:|:--------------------:|
| T1~T2 | 1~3 | 1대 |
| T3 | 4 | 2대 |
| T4 | 5 | 3대 |
| T5 | 6 | 3대 |

같은 설비를 여러 대 사면 취득가가 그대로 쌓이고 감가상각도 대수만큼 나간다.

### 4-5. 구매 vs 리스

**초반 현금난을 푸는 선택지**를 준다.

| | 현금 부담 | 회계 처리 | 총 지출 |
|---|---|---|---|
| **구매** | 취득가 전액 즉시 | 자산 계상 + 매주 감가상각 | 취득가 |
| **리스** | 없음 | 매주 리스료를 비용 처리 | 취득가의 **1.4배** |

```
주당 리스료 = 취득가 ÷ 내용연수 × 1.4
```

- 리스 설비는 **자산으로 잡히지 않는다** → 대출 한도(자산 × 0.5)도 안 늘어난다
- 언제든 해지 가능. 구매는 되팔면 장부가의 60%만 회수
- 회계적으로는 운용리스로만 다룬다 (금융리스·사용권자산은 도입하지 않음)

> 초반엔 리스로 버티다 자금이 쌓이면 구매로 전환하는 흐름이 만들어진다.

### 4-6. 노후화

장부가가 0이 되면 **노후 설비**가 된다.

- 미보유 페널티의 **절반**을 받는다
- 재구매(또는 리스 전환)하면 해소
- 결산 화면에 `노후 3건` 식으로 경고를 띄운다

### 4-7. 무형자산은 따로 두지 않는다

소프트웨어 라이선스 등은 회계상 무형자산(상각 대상)이지만,
**게임 안에서 유형자산과 행동이 완전히 동일**하다 — 사고, 쓰고, 낡는다.
계정만 하나 늘고 판단은 늘지 않으므로 **유형자산에 통합**한다.

### 4-8. 검산 — 지금 경제와 맞는가

현재 보상(§`business_model.REWARD_MULTIPLIER` 기준)과 대조했다.

| 사업 | 보상 | 필요 설비 (예) | 리스료 총액 | 보상 대비 |
|------|-----:|---------------|-----------:|---------:|
| T2 (8주) | $111,904 | BE 1대 | $7,900 | 7% |
| T2 (8주) | $111,904 | **AI 1대** | $25,850 | **23%** |
| T3 (12주) | $387,360 | AI 2대 | $77,500 | 20% |
| T3 (12주) | $387,360 | UIUX 2대 + FE 2대 | $35,600 | 9% |

- **AI 설비를 사서 쓰기엔 초반 자금($180k~500k)으로 벅차다.** 리스가 답이 되고,
  자금이 쌓인 뒤 구매로 넘어가는 흐름이 의도대로 생긴다
- UIUX·FE 조합은 부담이 작아 초반 진입로가 된다
- T1은 페널티 배율 0이라 설비 없이 그냥 한다 — 튜토리얼 구간이 보존된다

> 다만 **분야별 설비를 다 갖추려면 총 $470,000**이다. 시작 자금으로는 불가능하고
> 대출·리스 없이는 특정 분야에 전문화할 수밖에 없다. 이게 의도한 압박이다.

### 4-9. 이러면 생기는 판단

| 상황 | 플레이어의 고민 |
|------|----------------|
| AI·데이터 사업이 왔다 | 보상은 1.35배지만 GPU $180,000이 필요하다. 살까 빌릴까 거를까 |
| 모바일 랩이 낡았다 | 재구매할까, 모바일 종류를 안 받을까 |
| T3 수주 직전 | 설비 2대가 필요한데 1대뿐이다. 페널티를 안고 갈까 |
| 커머스만 계속 받았다 | 안전하지만 보상 배율 1.0이다. 슬슬 전환할까 |
| 자금이 빠듯하다 | 리스로 돌려 현금을 아낄까. 총액은 1.4배인데 |

**"우리 회사는 무엇을 하는 회사인가"** 가 자산 구성으로 답해진다.

### 4-10. 이 설계가 건드리는 기존 코드

설비 자체보다 **사업 생성 로직 변경**이 먼저다.

| 대상 | 변경 |
|------|------|
| `BUSINESS_NAMES` | 종류별 이름 목록으로 분리 |
| `Business.__init__` | 종류를 뽑고, 이름·보상 배율·목표 기간을 종류에서 가져온다 |
| `_build_tasks` | `random.sample(FIELDS)` → 종류의 핵심 필드 우선 배정 |
| `pick_tier` | 명성으로 종류도 함께 해금 |

> 종류 도입은 **재무 시스템 없이도 단독으로 의미가 있다.**
> 지금 "이름과 내용이 따로 노는" 문제를 먼저 고치고,
> 설비·재무는 그 위에 얹는 순서가 안전하다.

## 5. 대금 지급 구조 (선수금 도입)

지금은 완료 시 전액을 받는다. 여기에 **착수금**을 넣으면 초반 현금난이 완화되면서
선수금 계정도 자연스럽게 생긴다.

```
수주 시   계약금액의 30% 수령  →  현금 +, 선수금 +
진행 중   진행률만큼 수익 인식  →  선수금 감소, 다 쓰면 미청구공사 증가
완료 시   나머지 70% 수령      →  현금 +, 미청구공사 상계
```

| 시점 | 현금 | 선수금 | 미청구공사 |
|------|-----:|-------:|----------:|
| 수주 (30% 수령) | +30 | +30 | 0 |
| 진행률 30% | — | −30 | 0 |
| 진행률 70% | — | 0 | +40 |
| 완료 (70% 수령) | +70 | 0 | −40 |

## 6. 부채 — 대출 시스템

### 한도

```
대출 한도 = 자산총계 × 0.5 − 기존 차입금
```

자산이 없으면 못 빌린다. 설비를 사두면 한도가 늘어난다.

### 조건

| 종류 | 기간 | 주당 이자율 | 성격 |
|------|:----:|:----------:|------|
| **단기 운전자금** | 26주 | 0.35% | 급할 때. 비싸다 |
| **장기 시설자금** | 78주 | 0.18% | 설비 구매 목적에만 |

- 이자는 **매주** 발생하고 현금으로 나간다
- 만기에 원금 일시 상환. 못 갚으면 파산
- 명성이 높을수록 이자율 인하 (예: 12,000 이상이면 −0.05%p)

### 왜 필요한가

지금은 현금이 마르면 그냥 파산이다. 대출이 있으면
**"이자를 물고 버틸 것인가, 사업을 포기할 것인가"** 라는 선택이 생긴다.

## 7. 결산 주기

| 주기 | 무엇을 |
|------|--------|
| **매주** | 이번 주 손익 요약 (수익 / 노무비 / 감가상각 / 이자 → 주간 순이익) |
| **8주마다** | **결산**. 손익계산서 확정 + 대차대조표 스냅샷 + 이익잉여금 반영 |

- 8주로 잡은 이유: T2 목표 기간과 같아서 "사업 한 건 = 한 분기" 감각이 생긴다
- 결산 이력을 보관해 **분기별 추이**를 볼 수 있게 한다
- 주차를 넘길 때 토스트에 `이번 주 −$4,180` 식으로 순이익을 같이 띄운다

## 8. 화면 구성 (안)

**팀 & 기록** 모달에 `재무` 탭을 추가한다. 새 모달을 만들지 않는다.

```
[요약]  현금 $182,400   이번 주 −$4,180   8주 후 결산

[대차대조표]                    [손익계산서 · 이번 분기]
 자산                            수익
   현금          182,400          사업 수익      124,800
   미청구공사     40,300         비용
   설비           28,000           노무비         96,400
 ─────────────────                감가상각         2,400
 자산총계        250,700           이자             1,900
                                 ─────────────────
 부채                            순이익           24,100
   미지급급여          0
   선수금         18,000
   차입금        100,000
 자본
   자본금        300,000

```

- 이익잉여금이 음수면 붉게 표시

## 9. 판단이 필요한 것

1. **설비 페널티를 처리량에 걸 것인가, 성공 확률에 걸 것인가?**
   - 처리량: 기간이 늘어난다 → 인건비로 서서히 아프다 (§4 안)
   - 성공 확률: 완료 시점에 크게 터진다
   - → **처리량을 권한다.** 하드 게이트로 막지 않는 건 확정 (지금 착수 게이트가
     "경고 후 강행"이므로 일관된다)

1-b. **분야별 설비를 등급별로 세분화할 것인가?**
   - 지금 안은 "같은 설비를 여러 대"로 규모를 표현한다 (§4-4)
   - 대안은 Lv1/Lv2/Lv3 등급을 두고 업그레이드하는 방식
   - → **수용량 방식을 권한다.** 개념이 하나로 끝나고 책상과 같은 논리다

2. **노무비를 매출원가/판관비로 나눌 것인가?**
   - 나누면 "놀리는 인력 비용"이 보인다
   - 안 나누면 계정이 하나 줄어든다

3. **자본금을 늘릴 수 있게 할 것인가 (증자)?**
   - 투자 유치를 넣으면 자본금이 늘고 지분 개념이 필요해진다
   - 지금 범위를 넘으므로 **일단 제외**하고, 대출로만 자금을 조달한다

4. **파산 조건을 자본잠식으로 바꿀 것인가?**
   - 지금은 "급여 미지급 = 즉시 파산"
   - 회계를 넣으면 **자본총계 < 0 (완전자본잠식)** 이 더 자연스럽다
   - 다만 즉시성이 떨어져 긴장감이 줄 수 있다

5. **진행기준 수익인식을 실패한 업무에도 적용할 것인가?**
   - 진행률이 롤백되면 **인식했던 수익을 되돌려야** 한다 (역분개)
   - 회계적으로는 맞지만 "이번 주 수익 −$30,000" 같은 화면이 나온다
   - → 오히려 실패의 무게가 드러나서 괜찮을 수도 있다

## 10. 구현 순서 (착수 시)

1. `Ledger` 계정 구조 + 분개 헬퍼 — 기존 6개 현금 지점을 여기로 통과시킨다
2. 진행기준 수익 인식 (`progress_businesses`에 연결)
3. 착수금 / 선수금 / 미청구공사
4. 설비 + 감가상각
5. 대출 + 이자
6. 8주 결산 + 재무 탭 UI

1~2단계만 해도 "이익과 현금이 다르다"는 핵심은 성립한다. 3단계 이후는 선택이다.
